      What happens when you click a movie

      Every movie has a learned 64-dimensional vector. When you pick some films, the page averages their vectors and pushes that average through the user tower — a small two-layer network whose weights are shipped with this page — producing one vector that represents your taste. Every movie is then scored by a dot product against it, and the top 10 are shown.

      user_vector = normalise( user_mlp( mean( item_vectors[your picks] ) ) )
score(movie)  = user_vector · item_vector[movie]

      Why the user tower reads history, not a user ID

      The obvious design is nn.Embedding(n_users, dim) — one learned vector per user ID. It trains fine and scores fine, and it is useless in production: it can only represent users who existed at training time. A new signup has no row in that table, and neither do you.

      The first version of this project made exactly that mistake, which is why its demo could only replay pre-existing users like “user 437”. Rebuilding the user tower to encode the set of items you liked fixed it — and scored better too, improving NDCG@10 by around 19% over the ID-based version, because item co-occurrence generalises where a per-user parameter overfits.

      The two stages — and why only one of them shipped

      Stage 1 — retrieval. User and item are encoded separately into the same space, so scoring is one dot product. That restriction is the point: item vectors are computed offline and served from a vector index, so retrieval cost is independent of catalogue size. It is also why this page needs no backend at all.

      Stage 2 — ranking (LightGBM LambdaMART). Re-scores only the ~100 survivors using 28 features stage 1 structurally cannot represent, chiefly per-genre user×item crosses. LambdaRank optimises the order of the list rather than per-item probabilities.

      It made things worse, so it is not in the serving path. Measured across seeds, re-ranking cost roughly 19% NDCG@10 against retrieval alone. Two causes look most likely: the ranker trains on only ~938 lists with one positive each, which is very little signal for 28 features; and its strongest features are popularity and quality signals, which drag predictions back toward the popularity baseline that stage 1 already beats by a wide margin.

      An earlier version of this project reported the re-ranker helping by 5.7%. That number came from a weaker ID-based retrieval stage, a training run whose early stopping was reading the test set, and multithreaded training that was not reproducible. All three are fixed above, and the honest result reversed sign. It is kept in the repository and reported here rather than quietly deleted, because the measurement is the point.

      The bug that mattered

      The first working version lost to a popularity baseline and recommended obscure arthouse films to everyone. In-batch negatives sample items in proportion to popularity, so blockbusters appear as negatives in nearly every batch and the model learns to avoid them — popularity bias, running backwards.

      Fix: logQ correction — subtract each item's log sampling probability from its logit, cancelling the over-sampling penalty:

      corrected_logit(i, j) = raw_logit(i, j) − log Q(j)

      Applied at training time only. Both variants are kept in the code as a reproducible ablation.

      Honest limitations

      • This page runs stage 1 only. The LambdaMART re-ranker needs per-candidate feature computation; the table above is from the full offline pipeline.
      • Candidate recall@100 is ~0.54 — for nearly half of users the correct item never reaches stage 2. That ceiling means improving retrieval would pay far more than further ranking work.
      • The user vector is order-blind. Averaging item vectors cannot tell that you watched horror last week and comedies last year. A sequence model (GRU4Rec, SASRec) is the upgrade path.
      • MovieLens-100K is small and stops in 1998, so there is nothing recent to recommend. These numbers would not transfer unchanged to a production catalogue.
      • Training had to be pinned to a single thread to be reproducible — multithreaded float reduction was moving NDCG@10 by ±5% across identically seeded runs.
